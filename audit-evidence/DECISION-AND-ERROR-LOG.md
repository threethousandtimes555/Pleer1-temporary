## Важное предупреждение о репозитории

Этот журнал находится в **Pleer1-temporary — временном публичном репозитории**. Он предназначен для временного аудита и экспериментов, а не для хранения постоянной истории проекта.

- Не добавлять сюда пароли, токены, ключи API, персональные данные, приватные переписки, секреты или иные чувствительные сведения.
- Не переносить изменения из временного репозитория в основной Pleer1 без отдельного согласования.
- Перед удалением временного репозитория согласовать, какие безопасные записи и результаты нужно сохранить в основном проекте.
- Публичные записи должны содержать только информацию, которую допустимо раскрывать всем.

## Правила ведения журнала

1. Фиксируем гипотезы отдельно от подтверждённых фактов.
2. Проверяем выводы ChatGPT и Qwen независимо; совпадение двух моделей само по себе не считается доказательством.
3. Для каждого существенного вывода указываем проверку: исходный код, diff/commit, лог, артефакт CI, скриншот или воспроизводимый тест.
4. Не переписываем первоначальные предположения задним числом. Исправления добавляем новой записью или обновлением статуса с сохранением истории через Git-коммиты.
5. Если данных недостаточно, прямо пишем «не подтверждено» или «нужны дополнительные данные».
6. Отмечаем как ошибки моделей, так и ошибки процесса, тестов и инженерных решений.
7. Записываем успешные решения и регрессии, чтобы не повторять уже пройденные эксперименты.

## Статусы

- **Гипотеза** — возможное объяснение, ещё не проверено.
- **На проверке** — тест или независимый разбор выполняется.
- **Подтверждено** — есть воспроизводимые доказательства.
- **Опровергнуто** — проверка показала, что гипотеза неверна.
- **Частично подтверждено** — верна только часть предположения.
- **Нужны дополнительные данные** — имеющихся доказательств недостаточно.
- **Исправлено и перепроверено** — изменение внесено и повторная проверка прошла.

### Запись №018 — выяснение, почему прежний «найденный трек» запускался

- **Дата:** 18.11.2026
- **Область:** SearchModel / Jamendo / Player playback / корректность старого UI-теста.
- **Уточнение пользователя:** результат «Джем – я молодой вампир vamp» относится к Jamendo, а не подтверждает поиск отдельного YouTube-видео. Отдельно выяснить, почему этот результат вообще запускался.
- **Подтверждённый путь в коде:**
  1. Старый и текущий `SearchModel.run` запускает источники параллельно; если Jamendo включён и задан `client_id`, вызывается `Sources.jamendo`.

Старый тест проверял текст совпадения в общей выдаче и не фиксировал source tag, ID или YouTube video ID. Факт запуска — совместим с Jamendo-потоком и не является подтверждением YouTube.
- **Изменение регрессионного теста:** в рабочей ветке commit [e66d0557](https://github.com/threethousandtimes555/Pleer1/commit/e66d0557fad1c2c08b3e7fd081b6814132a8a001) заменил неоднозначный запрос `я молодой вампир vamp` на контрольный запрос `Crystal Castles Concrete`. Проверка по-прежнему требует accessibility identifier `search.result.youtube.track`, который назначается только трекам с YouTube ID-префиксом `y`, без playlist/radio ID.
- **CI:** run #29 [44204680947](https://github.com/threethousandtimes555/Pleer1/actions/runs/44204680947) на предыдущей версии теста ещё выполнялся; run #30 [44205081047](https://github.com/threethousandtimes555/Pleer1/actions/runs/44205081047) на обновлённом запросе находится в состоянии pending. ### Запись №035 — продуктовое решение: обычный поиск показывает треки первыми, коллекции — отдельным блоком

- **Дата:** 18.11.2026.
- **Область:** UX / архитектура YouTube search / будущая доработка.
- **Решение:** обычный запрос вроде `Concrete` должен в первую очередь возвращать самостоятельные музыкальные видео, но не обязан навсегда скрывать связанные плейлисты, YouTube Mix и другие коллекции. Предпочтительная модель выдачи — отдельные секции с приоритетом треков: сначала «Треки», затем «Плейлисты», «Миксы» и другие типы коллекций, если YouTube действительно вернул такие результаты. - **Важное различие:** классифицировать элементы по структуре renderer/type и идентификаторам YouTube, а не только по словам в названии. Слова «Mix», «Jam» или «Джем» могут быть частью названия самостоятельной композиции. Не превращать обычную песню в коллекцию по одному текстовому совпадению.

- **Статус:** продуктовое направление зафиксировано; реализация отложена до подтверждения текущего поиска на симуляторе и физическом iPhone.
- **Критерии будущей проверки:** запрос `Concrete` показывает самостоятельные видео вверху; если YouTube вернул связанные коллекции, они доступны отдельно ниже; явный запрос `crystal castles playlist` показывает коллекции; RD Mix не классифицируется как обычный плейлист; композиция с названием «Джем …» остаётся обычным треком, если её renderer — video.

#### 1. Исправление JS/WKWebView bridge

- **Подтверждённая причина по исходникам и предыдущему device log:** Swift вызывает `window.PleerYouTube.resolve(...)` через `WKWebView.evaluateJavaScript`. JS-функция была объявлена `async` и возвращала Promise. В логе физического устройства 19 ноября это проявлялось как `JavaScript execution returned a result of an unsupported type`; при этом асинхронная работа JS продолжалась и отправляла запросы.
- **Исправление:** commit [baa1835](https://github.com/threethousandtimes555/Pleer1-Lab/commit/baa18357e85d7b4bb10d251c37c67dad299c72c3). `resolve()` теперь синхронно запускает async IIFE через `void` и не возвращает Promise в WebKit. Результат/ошибка доставляется через `youtubeResolve` message handler, как и раньше.
- **Статус:** исходник исправлен; сборка и физическая проверка не проводились. Нельзя пока утверждать, что JS fallback работает полностью.

### Запись №049 — сравнение retry, expiry и AVPlayer lifecycle с Musike

- **Дата:** 19.11.2026.
- **Musike:** `web/src/player/player.ts` делает одну повторную попытку после media error; `explainStreamError` вызывает `forgetUrl` только после повторной ошибки. Поскольку `resolveAudio` кэширует URL до истечения срока, первая повторная попытка может снова получить тот же URL из cache. Это поведение не следует копировать без отдельной проверки.
- **Pleer:** при AVPlayer item failure, если активный поток пришёл из youtubei.js, `Player.itemStatus` сначала вызывает `YouTubeJSResolver.shared.forget(url:)`, затем выполняет одну ограниченную повторную попытку. Native Swift resolver не имеет stream cache, поэтому повторный resolve запрашивает новый URL. По исходникам это выглядит более надёжным для истёкшего/отозванного URL, но требует проверки на устройстве с реальным HTTP 403/ошибкой CDN.
- **Playback lifecycle:** Musike `MusikeAudio.swift` использует AVPlayer, User-Agent header, forward buffer 30 секунд, resolver duration вместо потенциально удвоенной AVPlayer duration, early-end guard и точную seek. Pleer `Player.swift` использует тот же User-Agent для сетевого YouTube asset, forward buffer 30 секунд, resolver duration, end observer, отдельный watchdog и guard от повторного completion; дополнительно сохраняет прямое управление AVPlayer, аудиопрерывания и системные remote commands.
- **Intentional architecture difference:** Musike держит native AVPlayer за WKWebView message bridge, Pleer использует AVPlayer непосредственно в SwiftUI/Player. Переносить web bridge целиком не требуется для parity по извлечению потока.
- **Небольшая диагностика:** `FavoritesAudioCache.deleteFiles` пишет `reason=unfavorited` и при явном удалении загрузки пользователем. Это не влияет на аудио, но может исказить диагностику; поправить reason на фактический контекст удаления до финальной проверки журнала.
- **Итог:** retry/expiry и основная AVPlayer duration/buffering логика Pleer не отстают от Musike по статически просмотренным участкам; в retry у Pleer есть более явная инвалидация JS cache. Это source comparison, не runtime proof.
- **Остаются открыты:** WebM vs AAC/MP4, общая дедупликация native resolver, удаление активного локального файла, UI мобильного согласия в фирменном стиле, двойной трафик при stream+download.

### Запись №051 — сетевые переходы, проверка аудиофайла и безопасное удаление офлайн-трека

- **Дата:** 19.11.2026.
- **Ветка:** `feature/youtubei-js-ios-fallback-2026-11-19`.
- **Сетевые переходы:** при изменении доступности сети или активного интерфейса (Wi-Fi/cellular) текущая загрузка отменяется, трек возвращается в начало serial queue, после завершения старого worker очередь запускается заново. Согласие на мобильную загрузку сохраняется в пределах текущей сессии приложения; если согласия нет, очередь ждёт Wi-Fi/решения пользователя.
- **Ограничение размера:** вместо полного скачивания с последующей проверкой используется URLSessionDownloadDelegate. Проверка реального поведения delegate ещё требуется на iPhone.
- **Проверка содержимого:** разрешённые MIME ограничены audio/mp4, audio/x-m4a, audio/aac, пустым или application/octet-stream. Дополнительно проверяется сигнатура: ISO-BMFF ftyp для MP4/M4A и ADTS sync для AAC. HTML и неизвестные данные не принимаются. WebM по-прежнему намеренно не поддерживается.
